# 共通ランタイムを触るときの注意

ここは**全ゲームの土台**。1行変えると過去のゲームが全部壊れうる。

## 変更したら必ず

```bash
npm run selftest     # 機種・操作・リプレイの配管が生きているか（1秒）
npm run fun:all      # 全ゲームのゲートを回す（数字が変わっていないか見る）
```

selftest が要るのは、**登録済みのゲームが使っていない機能はゲートでは踏まれない**から。
steer / type / aim や機種の配管は、それを使う1本目が出るまで fun:all では検査されない。

⚠️ **もうひとつの盲点: playtest の指紋はここ（ランタイム）を含まない。**
指紋は `src/games/<slug>/` の2ファイルだけなので、ランタイムを変えても
「人が遊んだ記録」は古くならない（そうしないとランタイムを触るたび全ゲーム遊び直しになる）。
つまり**ゲートの数字が動かない範囲の手触りの変化（入力・シェル）は、機械では捕まらない**。
入力やシェルの挙動を触ったら、数字が緑でも自分で1回遊んで確かめること。

数字が変わったら、それは既存のゲームの手触りが変わったということ。
意図した変更でないなら戻す。

前回の数字は `docs/records/gate/<slug>.json` に記録してあり、
**大きく動くと `npm run fun` が落ちる**（CI でも同じ）。意図した変更なら記録を更新する。

```bash
npm run fun -- <slug> --record    # いまの数字を新しい基準にする
```

記録の更新は「手触りを変えた」という宣言なので、**コミットに含めて理由を書く**こと。

## 変えてはいけないもの

| 対象 | 理由 |
|---|---|
| **ゲームが1本でも出ている機種の解像度・描画方式**（platforms.ts） | その機種の既存ゲームの座標が全部ずれる。keitai の 240×320（= `VIRTUAL_W/H`）は既存全ゲームの座標基準なので永続。まだゲームの無い機種は最初の公開まで調整してよい |
| `FIXED_DT`（1/60） | 難度カーブが全部変わる。可変 dt にすると再現性が消える。**全機種共通** |
| `advance()` を通さない更新経路 | 実プレイとゲートで挙動が分かれると、ゲートの数字が意味を失う |
| `toInput()` を通さない `Input` の組み立て | ボット・実プレイ・リプレイで作り方が分かれると「リプレイだけ結果が違う」が起きる。実際に `aim` でそうなっていた |

## 入力を足すときは、記録も一緒に足す

リプレイは「種＋操作の記録」だけで再現している。
`Input` に新しいものを足したら、**GameShell の `toLogFrame` にも足す**こと。
記録していない入力は、リプレイでは無かったことになる。

記録は `meta.control` が使う分だけ残している。
タップのゲームを1フレーム1ビットのままに保つための作りなので、ここをまとめて全部残す形にしない。

## 足すときの判断

**2本以上のゲームで実際に必要になってから**足す。
「あると便利そう」で足したものは、だいたい1本でしか使われず、読む量だけが増える。

例外は「全ゲームの体験を良くするもの」（リトライの速さ、惜しさの表示、共有）。
これは1本しか無くても入れてよい。ゲーム側の作業を減らす方向の投資だから。

## ここは lint の「やってはいけないこと」の対象外

`requestAnimationFrame` も `window` も `Math.random()`（実プレイの種）も、**この層が持っている**。
だから `eslint.config.mjs` の `asobuild/games` は `src/games/**` にだけ効かせてある。

裏を返すと、**ここに書いたものは機械に守ってもらえない**。
ループ・乱数・描画を触るときは、それがゲーム側へ漏れていないかを自分で見ること。

## 依存を増やさない

外部ライブラリを入れない。物理エンジンも描画ライブラリも要らない。
15分で作るゲームに必要な計算は、四則演算と `Math.abs` / `Math.min` で足りる。
