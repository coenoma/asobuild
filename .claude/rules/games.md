# ゲーム実装の規約

## state の作り方

- フラットに持つ（ネストした構造にしない）。`{...s}` の浅いコピーで済む形を保つ
- 調整する数値（速度・判定幅・ライフ数）は **ファイル冒頭の定数**にまとめ、名前をつける
  → 収録中に「ここの数字を上げて」で通じるようにするため
- 演出専用の値（点滅タイマー・画面揺れ）も state に持つ。`draw` の中で時間を進めない

## step の書き順

この順に書くと、判定の取りこぼしが起きにくい。

1. タイマー類を減らす（クールタイム・演出）
2. 難度パラメータを更新する（`n.speed = 基準 + s.time * 係数`）
3. 物を動かす／画面外を捨てる
4. **通り過ぎたものの判定**（取り逃がし）
5. 出現
6. 入力の処理
7. 終了判定（`n.over = true`）

4 を 6 より先にやる。逆にすると「押したのに取り逃がし扱い」が起きる。

## やってはいけないこと

### `npm run lint` が見ているもの

破ると落ちる（`eslint.config.mjs` の `asobuild/games`）。落ちたときは日本語で直し方が出る。

- `Math.random()` / `Date.now()` / `performance.now()` を使う（再現性が壊れる）
- `setTimeout` / `setInterval` / `requestAnimationFrame` を自前で呼ぶ（ループは共通シェルが持っている）
- `window` / `document` / `localStorage` を触る（Node 上のゲート実行で落ちる）
- 生の `#hex` で色を書く（色は `palette.ts` のキー名で指定する）

### まだ人の目だけが頼りのもの

- 引数の `state` を書き換える（`s.score += 1` ではなく `n.score += 1`）
- `draw` の中で state を変える

**機械で見られるようにできたら、上の組へ移すこと。**
書いてあるだけのルールは、そのうち必ず破られる。

## bot() の書き方

「上手い人ならこう動く」を10行で。完璧でなくてよいが、**弱すぎると `上手ければ続く` が不当に落ちる**。

```ts
bot(s) {
  if (s.cooldown > 0) return { press: false };        // 押せない状況を先に弾く
  const target = 次に処理すべきもの;
  if (!target) return { press: false };
  const per = s.speed / 60;                            // 1フレームの移動量
  return { press: target.y + per >= 判定ライン };       // 次フレームで跨ぐなら今押す
}
```

判定ラインを跨ぐ瞬間を予測して押す形にすると、速度が上がっても正確に動く。
「距離が◯以内なら押す」だと、速度が上がったときに窓を飛び越して押せなくなる。

## novice() は、書かなくていいなら書かない

「何も分かっていない人」役は共通のでたらめボットが担っている。
`novice()` を書いてよいのは、**そのでたらめボットでは構造的に一度も成功できない**ときだけ。

いまのところ該当するのは `type`（タイピング）だけ。
でたらめに文字を打つ人は一度も正解を打てないので、
「初見でも点が入るか」が、ゲームの出来ではなくボットの都合で決まってしまう。

```ts
// 打てるが、この遊びを知らない人。ゆっくり打って、ときどき間違える
novice(s, rng) {
  if (s.cooldown > 0) return { press: false };
  const want = s.word[s.done];
  return { press: false, typed: [rng.chance(0.25) ? rng.pick(NEAR_KEYS) : want] };
}
```

🔴 **ゲートを通したいから書く、は禁止。** ここは「下手な人」であって「そこそこの人」ではない。
書くと `npm run fun` に「novice() が担っています」と出るので、隠せない。

## 機種（platform）を選んだら

- 既定は `keitai`（240×320 縦）。それ以外は **meta に `platform` を書く**（[platforms.md](../../docs/design/platforms.md)）
- 座標は `VIRTUAL_W/H` ではなく `PLATFORMS.<機種>.w / .h` を基準にする（keitai は同じ値）
- 横長機種のレイアウトは縦持ちの並びをそのまま使わない。HUD は上帯1本にまとめ、主役は横に走らせる
- **その機種の最初のゲームを公開した時点で、機種の寸法は固定される**

## 操作方式ごとの注意（steer / type）

基本は `tap` / `hold` / `tap-hold` / `aim` の4つで、**まずこの中で作る**。
下の2つを使ってよいのは、**その操作を1ボタンに置き換えたら題材そのものが消えるとき**だけ
（判断は [fun-doctrine ①](../../docs/design/fun-doctrine.md)）。

### steer（曲がる）

- `input.steer` は **-1 / 0 / +1 の3値**。中間の角度は入力側では作らない
- 滑らかさはゲーム側で作る。「いまの角度をこの向きへ少しずつ寄せる」形にすること
  （入力側で滑らかにすると、ゲームごとに感度がばらついてシリーズの手触りが揃わなくなる）
- 押しているあいだは `hold` も立つ。アクセルや踏ん張りに使ってよいが、**足す軸はここまで**

### type（打つ）

- `input.typed` はそのフレームで打たれた文字の配列。ほとんどのフレームは空
- **スマホで遊べない。** 代わりに画面へ「パソコン向け」と出る
- スペースは「文字」であって押下ではない。始める・もう一回は Enter とタップが担う
- **日本語入力がオンだと文字が来ない。**「かなをオフに」を画面のどこかで必ず伝える
- `novice()` が要る（上記）

## ターン制のゲームを書くとき

`step` はターン制でも毎フレーム呼ばれ続ける。「入力待ち」の状態では何もしないだけでよい。
`setTimeout` で待たないこと（再現性が壊れる）。

- 待っている状態も `state` に持つ（`phase: 'さいころ' | 'えらぶ' | 'すすむ'` など）
- 演出の時間も `state` のタイマーで進める。`draw` の中で時間を進めない
- **ターン数で終わるゲームは、面白さゲートの効かない項目が出る**
  → [genre-map.md](../../docs/design/genre-map.md) の「ターン数で終わるゲーム」を先に読む

## reason() は必ず書く

死因はリザルト画面にそのまま出る。プレイヤーが次に何を直せばいいか分かる文にする。

- ⭕️「見のがしが多すぎた」「差戻にハンコを押した」
- ❌「ゲームオーバー」「ライフが0になった」

死因は「そうなった瞬間」に `state.deathReason` へ入れる。最後にまとめて判定しない。

## 遊んでいない人にも伝わるように描く

このゲームは動画に映る。**コントローラーを持っていない人**が画面だけを見て、
うまくいっているのか・危ないのか・失敗したのかが分かる必要がある。

- 危険なものは常に同じ色（`bad`）にする。役割を色で固定する
- 残機は常時表示する（減った瞬間が見えるように）
- 失敗は画面全体で示す（`addShake()` ＋ 一瞬の色）
- 主役の指標は1つに絞る。小さな画面で2箇所を同時に見せない（どの機種でも）
- やられた瞬間の絵に手をかける（`launchTumble()`）

判断のしかた: **音を消して30秒眺めて、何が起きているか分かるか。**
考え方は [docs/design/broadcast-design.md](../../docs/design/broadcast-design.md)。

## 中断（やめる）は作らない

プレイ中に抜ける仕組みは共通シェルが持っている（ESC か「やめる」ボタン →「つづける／ここでやめる」）。
ゲーム側でポーズやメニューを作らない。

- 中断中は `step` が呼ばれないので、時間もスコアも止まる
- 途中でやめた場合もそこまでの記録は残る（死因は「とちゅうでやめた」）

> リトライの前に確認を挟まない（[fun-doctrine](../../docs/design/fun-doctrine.md) ⑤）のと、
> プレイ中に抜けられることは別の話。抜け道が無いと、電話が来ただけで記録を捨てることになる。

## 手触りは自前で書かない

先行入力・猶予・ヒットストップ・画面ゆれ・弾みは `src/arcade/feel.ts` にある。
自前で似たものを書くと、ゲームごとに数値がばらついてシリーズとしての手触りが揃わなくなる。

```ts
export interface MyState extends BaseState, FeelState {}

init() { return { ...createFeel(), score: 0, over: false, time: 0, /* ... */ }; },

step(s, input, dt, rng) {
  const n = { ...s };
  if (!feelTick(n, input, dt)) return n;   // 「止め」の最中は世界を進めない
  if (takeTap(n) && 条件) { /* 先行入力つきの判定 */ }
  ...
}
```

何がなぜ効くのか・目安の数値は [docs/design/feel-catalog.md](../../docs/design/feel-catalog.md)。
新しく効く工夫を見つけたら、実装を `feel.ts` に、理由をカタログに足す。

## 出す前に見る落とし穴

ゲートでは拾えないが、遊ぶと必ず言われるもの。実際に指摘されたものだけを並べてある。

- [ ] **どの操作にも反応があるか。** 成功でも失敗でもない「無反応」は、遊ぶ人にはバグに見える
- [ ] **色に意味を持たせたなら、凡例が画面にあるか。** 色の意味は説明しないと伝わらない
- [ ] **読ませたい文字を `line` で描いていないか。** 薄すぎて出ていないのと同じになる
- [ ] **判定の瞬間が見た目とズレるなら、外したときの手がかりを返しているか**（早い／遅い、右／左）
- [ ] **音を消して30秒眺めて、何が起きているか分かるか**

詳しくは [feel-catalog.md](../../docs/design/feel-catalog.md) G章。
