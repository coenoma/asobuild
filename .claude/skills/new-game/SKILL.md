# ゲームを1本作る

お題は一言でよい（「ポテトのゲーム」「傘」「コピー機」）。そこから遊べる状態まで持っていく手順。

**作る規模は制作時間によらず一定**にする。1プレイ30秒〜2分、一気に遊んで15〜30分でひととおりやりきれる規模。
制作時間が長い企画（1日・7日）でも、ステージやモードを増やさず、密度を上げる方に使う。

作る前に [docs/design/fun-doctrine.md](../../../docs/design/fun-doctrine.md) を読むこと。

---

## 0. 遊びの型を決める

まず [genre-map.md](../../../docs/design/genre-map.md) で `meta.genre` を選ぶ。
**型が変わると、面白さゲートが見る項目そのものが変わる**（育てるものに「放置すると死ぬ」を
当ててしまうと、正しく作れているのに落ちる）。

| 型 | 何をしている時間がいちばん長いか |
|---|---|
| `action` | 避けている・タイミングを合わせている（**迷ったらこれ**） |
| `puzzle` | 手を考えている |
| `nurture` | 世話をしている・待っている |
| `chance` | 引いている・集めている |
| `oneshot` | 探している・解いている（1回で終わり） |

## 1. ルールを1行にする（ここが企画）

お題そのものはゲームではない。**題材 × 型** でルールにする。
以下は `action` の場合の型。他の型は genre-map.md の各節を見る。

### 動きの型（action の場合、この5つから選ぶ）

| 型 | 操作 | 中心にある快感 | 例 |
|---|---|---|---|
| **A 来たものを処理する** | tap | タイミングが合った | 流れてくる書類にハンコ |
| **B 溜めて放つ** | hold | 加減がうまくいった | 長押しで伸ばして向こう岸へ |
| **C 避け続ける** | tap | 反射で切り抜けた | 障害物をジャンプで越える |
| **D 積む・並べる** | tap | ギリギリで置けた | 落ちてくる物を積み上げる |
| **E 見分ける** | tap | 一瞬で判断できた | 本物と偽物を選り分ける |

迷ったら **A**。当時のケータイゲームで一番多く、実装も速く、腕前の差が出やすい。

### 決めること（この5つだけ）

1. **押すと何が起きるか**（1つだけ）
2. **押してはいけないものは何か** ← 必ず入れる（無いと連打ゲームになる）
3. **何を失敗するとライフが減るか**
4. **時間とともに何が上がるか**（速度／間隔／量のどれか1つ）
5. **称号を3〜5段階**（最初は1〜2プレイで届く、最後は一気に遊んで15〜30分で届く）

5 を後回しにしない。これが無いと「もう一回やる理由」と「やりきった」が生まれず、
どれだけ手触りを磨いても3回で飽きる。

### 出力（実装に入る前にこの形で確認する）

```
題材: マックのポテト
型: A（来たものを処理する）
押す: 落ちてくるポテトを紙袋でキャッチ
押さない: 焦げたポテトは取ってはいけない
失敗: 良いポテトを落とす／焦げを取る
上がる: 落下速度と本数
称号: 50=バイト / 150=店員 / 400=店長 / 900=エリアマネージャ
タイトル: ポテトキャッチ（slug: potato-catch）

── 見せる前提の確認（必ず添える）──
権利: 着想元なし（オリジナル）
      ※着想元があるなら「何を借りて何を自作するか」を書く
映える瞬間: 焦げを掴んで画面が赤くなる瞬間／取り逃がしが3つ重なる終盤
結果が気になる点: 「店長まで行けるか」
成否の見えやすさ: 良い＝黄色／焦げ＝黒、残機は上に3つ常時表示
```

この4行は飾りではない。**動画として面白いかは、ゲームとして面白いかと同じくらい重要**で、
ここが書けない案は、遊べても番組の題材としては弱い。
考え方は [docs/design/broadcast-design.md](../../../docs/design/broadcast-design.md)。

### 既存作を下敷きにする場合

[docs/design/rights-and-originality.md](../../../docs/design/rights-and-originality.md) を読んでから始める。

- 借りてよいのは**遊びの仕組み**だけ（自動で前進する／1ボタンで跳ぶ／距離を競う）
- キャラ・絵・UI・音・ステージ配置・タイトル・コードは**すべて自分で作る**
- `meta.inspiration` に「何から着想し、何を借り、何を自作したか」を必ず書く
- 作りながら「公開版ではもっと離した方がよい」と思ったら、**黙って進めずその場で言う**

収録中なら、ここまでを口頭で読み上げると視聴者にも伝わる。

## 2. 雛形を出す

```bash
npm run new -- <slug> --title "タイトル" --howto "あそびかた" --control tap --constraint "制約"
```

- `--howto` は20文字以内。読まなくても分かる一行
- `--control` は `tap` / `hold` / `tap-hold` / `aim`
- `--constraint` は収録の制約（例: `マックのポテトM`）。一覧に出る

## 3. `step` と `draw` を書く

雛形の TODO を埋める。書く順序と禁止事項は `.claude/rules/games.md` に従う（触れば自動で読まれる）。

**この段階で凝らない。** 形が分かる四角と丸で先に成立させ、余った時間で見た目を足す。

## 4. 面白さゲートを回す

```bash
npm run fun -- <slug>
```

落ちた項目の `→` の指示から直す。**推測で直さない。** 数字を見て、直して、また回す。
よくある落ち方と対処は [tune-game スキル](../tune-game/SKILL.md) にまとめてある。

## 5. 自分で3回遊ぶ

```bash
npm run dev    # http://localhost:3020/g/<slug>
```

ゲートが全部緑でも、遊んで「もう一回」と思わなければ作り直す。
確認するのはこの3つ。

- 説明を読まずに何をすればいいか分かったか
- 最初の10秒で1回失敗したか
- 死んだあと、指が勝手にもう一回押したか

## 6. 仕上げて公開

```bash
npm run check    # 型・全ゲームのゲート・ビルド
```

通ったらコミットして push（`main` で本番、ブランチなら Vercel プレビュー）。
コミットメッセージは日本語で「◯◯を追加」。

## 時間が足りないとき

削る順: 見た目 → 音 → 演出。
**削らない**: `bot()`、`reason()`、難度の上昇、押してはいけないもの。
未完成のまま撮影が終わったら、撮影後に仕上げてから公開する（動画では「このあと直しました」と言う）。
