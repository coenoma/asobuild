# 既存作を調べて、持ち帰る

目的は「詳しくなること」ではなく、**次に作るゲームに効く工夫を数値で持ち帰ること**。
運用ルールと法的な線引きは [docs/research/README.md](../../../docs/research/README.md) を必ず先に読む。

---

## 0. 先に決める：何を持ち帰りたいのか

漠然と調べ始めると、当時の思い出話で終わる。最初に1行で書く。

> 例:「1ボタンで走り続けるだけのゲームが、なぜ何度も遊ばれたのかを特定する」
> 例:「単純作業のくり返しなのに飽きない、その刻み方を特定する」

## 1. 事実を集める（30〜60分）

WebSearch / WebFetch で、**一次情報から**当たる。

- 公式サイト・公式の発表（配信時期、DL数、価格、対応端末）
- 開発者インタビュー・振り返り記事（**いちばん価値が高い**。設計意図が直接書いてある）
- 当時のレビュー・感想（何が語られていたか＝何が刺さったか）
- 「◯◯ 開発秘話」「◯◯ なぜ流行った」「◯◯ 周年」で探す

数字には必ず出典URLを付ける。**出典のない数字は書かない**。

## 2. 実際に触る（ここを飛ばさない）

- 移植版・後継作・公式の配信があるなら遊ぶ
- 無ければ実況動画をコマ送りする（`,` / `.` キー。動画のfpsを先に確認する）
- 測るもの: 押してから反応までのフレーム／最初の1点までの秒数／最初の失敗までの秒数／
  失敗から再開までの秒数／難度が上がりきるまでの秒数

> 映像からの計測には限界がある（配信のfps・入力ラグ）。
> 正確に出せない値は `推測:` とラベルし、**それらしい数字を実測のように書かない**。

## 3. テンプレートを埋める

```bash
cp docs/research/_template.md docs/research/<名前>.md
```

上から埋める。**埋まらない欄は消さずに「未調査」と書く。**
消すと「調べた上で該当なし」なのか「調べていない」のか分からなくなる。

特に §4「作り込みの工夫」が本命。ここが薄いまま次へ進まない。

## 4. 持ち帰るものを分ける

§6 で3つに仕分ける。

| 分類 | 行き先 |
|---|---|
| 今も効く工夫 | [docs/design/feel-catalog.md](../../../docs/design/feel-catalog.md) に追記。実装できるものは `src/arcade/feel.ts` へ |
| 当時だから効いた事情 | 調査ファイルに記録だけ。実装に持ち込まない |
| 効かなかった・再現しても意味がない | カタログの「効かなかったもの」へ |

カタログに足すときは **数値・理由・出典（この調査ファイルへのリンク）** をセットで書く。

## 5. 作る

[new-game スキル](../new-game/SKILL.md) に渡す。
このとき、調査で特定した工夫を**具体的な数値として**指定する。

> 例:「先行入力0.12秒、猶予0.1秒、成功時ヒットストップ0.05秒、
>     最初の1点は3秒以内、失敗から再開は0.8秒、称号は4段階」

**元作品の名前・キャラ・見た目を持ち込まない。** 持ち込むのは設計の原理だけ。

## 6. 検証する

調査ファイルの §7 に、元作品と自作の数字を並べる。

```bash
npm run fun -- <slug>    # 数字で見る
npm run dev              # 実際に遊ぶ
```

ゲートが全部緑でも、**元と同じ気持ちよさが出ていなければ未達**。
足りないときは §4 に戻る。「何が足りないか」が言葉にできれば、それがカタログの次の項目になる。

---

## よくある失敗

| 失敗 | どうなるか |
|---|---|
| 遊ばずに記事だけで書く | 当時の宣伝文句をなぞるだけになり、作り込みが何も分からない |
| 「テンポが良い」で止める | 実装できない。秒・フレーム・pxまで落とす |
| 当時の事情をそのまま持ち込む | 「当時っぽいけど今遊ぶと退屈」なものができる |
| カタログに反映せず終わる | 次のゲームに何も残らない。調査の価値は蓄積にしかない |
