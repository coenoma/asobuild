# 機種の地図

アソビルドの射程は**2000年前後〜2000年代なかばの遊び文化**で、ガラケーだけではない。
「どの画面で遊ばれていたか」を機種として1プリセットにまとめ、`meta.platform` で選ぶ。

[genre-map.md](./genre-map.md) が「遊びの型 → 面白さゲートの見る項目」を決めるのに対し、
ここは「機種 → 画面の寸法・向き・描画の質感・入力の想定」を決める。**型と機種は直交**する。
アクションをケータイでもゲーセンでも作れるし、ゲーセンでパズルも作れる。

実物の値は [src/arcade/platforms.ts](../../src/arcade/platforms.ts)。

---

## 3機種

| | `keitai`（既定） | `flash` | `arcade` |
|---|---|---|---|
| 何か | 2000年代なかばのカラーケータイ | 2000年前後〜の個人サイトの Flash ゲーム | 90年代末〜2000年前後のゲームセンター |
| 解像度 | 240×320 **縦** | 550×400 **横**（Flash MX の既定ステージ） | 384×224 **横**（CPS2 基板の実寸） |
| 描画 | ドット（拡大補間なし） | **なめらか**（当時からベクター描画） | ドット |
| パレット | keitai 10色 | flash 10色（白地に原色） | arcade 10色（暗い店内で光る色） |
| 入力の想定 | タップ／1ボタン | キーボード・マウス（**タイピングはここ**） | レバー＋ボタン＝**ゲームパッド対応** |
| スマホ | ◎ 本領 | △ 横長で小さくなる。type は遊べない | △ 横長で小さくなる |
| 向く遊び | 反射・1ボタンもの全般 | タイピング・マウスもの・診断 | レース・ベルト・格闘・シューティング |

### 選び方

1. **迷ったら keitai。** いちばん速く作れて、スマホで遊べて、シリーズの本流
2. その遊びが**当時どの画面で遊ばれていたか**で選ぶ（タイピング→flash、筐体もの→arcade）
3. 機種を豪華にしても**規模は変えない**（fun-doctrine §0）。1プレイ30秒〜2分・15〜30分でやりきる、は全機種共通

### 描画方式が機種で違う理由

keitai / arcade はドットが時代の実物。flash は当時から**ベクター描画**で、
寿司打もドット絵ではない。だから flash だけ補間ありで描く。
シリーズの統一感は、窓枠・パレットの規律・書体で担保する。

flash では Painter の `sprite()`（ドット絵API）は浮くので使わない。
主役は `circle` / `poly` / `line` と大きめの文字（当時の Flash の絵はそれでできている）。

---

## 🔴 変えてはいけないもの

**その機種でゲームが1本でも公開されたら、寸法と描画方式は変えない。**
変えると、その機種の既存ゲームの座標が全部ずれる（[.claude/rules/arcade.md](../../.claude/rules/arcade.md)）。

まだゲームが1本も無い機種（flash / arcade）は、最初の企画で実際に作りながら
調整してよい。**最初のゲームを公開した時点で固定される。**

---

## ⚖️ 機種がリッチになるほど、権利の注意が上がる

keitai の 10色ドットは「寄せようにも寄せられない」という安全装置を兼ねていた。
arcade の 384×224 は、**当時の実物の見た目に実際に寄せられてしまう**解像度になる。

- [rights-and-originality.md](./rights-and-originality.md) の「元作品を知っている人が誤認するか」テストの重みが上がる。とくに格闘（キャラの構え・技の絵は強烈に識別的）とレース
- **本物の3D（ポリゴン）は器の外。** Painter は2Dで、疑似3D（スキャンライン道路・拡大縮小）までにとどめる。これは実装の制約であると同時に、距離の保険でもある

## 増やすとき・広げるときの手順

### 機種を増やすとき

genre-map と同じ考え方で、**既存の3機種で説明できない画面の遊びを作りたくなったとき**だけ。
1本のために足すか迷ったら、まず既存機種に収められないかを考える。

4点セットで必ず一緒に更新する:

1. `PlatformName`（types.ts）
2. `PLATFORMS`（platforms.ts）
3. この地図
4. 必要なら palette.ts にテーマを対で足す

### パレットを広げるとき（例: アーケードの32色化）

色数を増やすのは、**最初にその機種の企画で実際に足りなくなったとき**。
キー名を増やす形で行い（`Palette` interface → 各テーマ）、用途の無い色を先に並べない
（読む量が増えるだけ——arcade.md「必要になってから」）。生の `#hex` 禁止と lint はそのまま効く。

### 複数ボタンを開くとき（例: 格闘）

いまの入力は「押す」1系統＋機種の例外（steer / type）。格闘をやるなら最低でも
移動＋2ボタンが要るが、**最初の格闘企画が来るまで実装しない**。

- 器はできている: `Frame` 型にフィールドを1つ足し、`toLogFrame` に記録を足すだけ（リプレイ関所が取りこぼしを検出する）
- 凝縮の方向: **2ボタン格闘は成立する**（移動＋攻撃2種で読み合いは作れる。Divekick が証明済み）。6ボタンを目指さない
- 手順: `Input`/`Frame`/`BotAction` に追加 → `toLogFrame` → `InputSource`（キー＋パッドの写像）→ fun-doctrine ① の例外表 → この地図

### 音を機種ごとにするとき

いまは全機種が矩形波シンセ（sfx.ts）。FM 音源風などの機種の音色は、
**2機種目でそれが欲しくなってから**。1機種のためには足さない。

## 動画・収録との関係

機種は動画の絵作りも変える（縦長の画面と横長の画面では収録レイアウトが違う）。
横長機種の初回収録の前に [収録レギュレーション](../guides/収録レギュレーション.md) と
[recording スキル](../../.claude/skills/recording/SKILL.md) の画面配置を見直すこと。
