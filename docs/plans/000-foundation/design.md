# 設計: アソビルドの基盤

> 2026-08-11 作成。この基盤をなぜこう作ったかの記録。
> 後から「なぜこうなっているのか」を掘り返さなくて済むように残す。

## 何を解こうとしているか

YouTube「アソビルド」で、制約のなかでミニゲームを量産する。
そのとき困るのは次の3つで、これを**仕組みで解く**のがこのリポジトリの目的。

1. 毎回ゼロから作ると、面白さの担保が作者の調子に左右される
2. 面白いかどうかを判断するのに時間がかかり、制作時間を食う
3. 過去の学びが次に活きず、毎回ふりだしに戻る

## 決めたこと

### 1. 作るものの規模を固定した

制作時間は企画ごとに変わる（コーヒー1杯〜7日）が、**規模は毎回同じ**。

- 1プレイ 30秒〜2分
- 一気に遊んで15〜30分でひととおりやりきれる
- 時間が余ったら要素を増やさず密度を上げる

時間が長い企画で規模を広げると、作りきれず遊びきれないものができる。
規模を固定したことで、制作時間の違いは「密度の違い」として現れる。

### 2. ゲームを純粋関数として書く規約にした

`step(state, input, dt, rng)` が新しい state を返す形に統一した。

- 同じ入力から必ず同じ結果になる → **ボットに何百回も遊ばせて統計が取れる**
- 実プレイもボット試験も `advance()` という同じ経路を通る → 数字と実機が食い違わない
- 乱数は `rng` 経由、時間は `state.time`。`Math.random()` / `Date.now()` を禁止した

この制約が、後述の面白さゲートを成立させている。**ここを緩めると全部が崩れる。**

### 3. 面白さゲートを作った

3種類のボット（放置・でたらめ・上手い）に数百回プレイさせ、11項目を数字で判定する。

判定するのは「面白いか」ではなく「**面白くなりようがない状態でないか**」。

- 放置しても死なない → 緊張がない
- 初見で点が入らない → 1回で帰る
- 連打で勝てる → 判断がない
- 腕前でスコアが変わらない → 運ゲー
- 上手いと永遠に終わらない → 記録が出ない
- 毎回同じ点で終わる → 3回で飽きる
- 最後の称号に届くまでが長すぎる／短すぎる → やりきれない

落ちた項目には**直し方**を出す。ここが肝心で、感想ではなく指示が出るから短時間で直せる。

> `bot()` を必須にしたのは意図的。10行のボットが書けないゲームは、
> ルールが一言で説明できていない。書けるかどうか自体がフィルタになる。

### 4. 称号（`meta.goals`）を仕組みに入れた

スコアアタックだけだと「やりきり感」が出ない。3〜5段階の称号を置き、

- 最初は1〜2プレイで届く（最初のごほうび）
- 最後は一気に遊んで15〜30分で届く（1セッションの長さ）

ゲートが「上手いボットが最後の称号に届くまでの想定時間」を実測して判定する。
**規模の要件を数字で担保できる**ようになった。

### 5. 手触りを `feel.ts` に切り出した

先行入力・猶予・ヒットストップ・画面ゆれ・弾み・やられ演出。
面白さの多くはこの層にあるが、毎回思い出して書くと数値がばらつく。

やられた後も 0.85 秒 `step` を回す設計にしたのは、
**失敗の絵がそのゲームの記憶になる**から（落ち方が語り継がれる、という現象）。
落下の重力を意図的に弱めてある（現実より遅く落ちるほうが可笑しく、見せる時間も生まれる）。

### 6. 調査を蓄積の仕組みにした

既存作を調べたら `docs/research/` に残し、そこで見つけた工夫を
`docs/design/feel-catalog.md` と `feel.ts` に流す。

**調査するたびに次のゲームが強くなる**構造。調べっぱなしにしない。
憶測と実測を書き分けるルール（`実測:` `出典:` `推測:` のラベル）を必須にした。

### 7. 見た目は 240×320 の拡大で作る

QVGA 縦持ちに描いて `image-rendering: pixelated` で拡大する。

- 何を描いても勝手に粗くなる → 当時の見た目が自動で手に入る
- ドット風 Web フォント（数MB）が不要になる
- 色はパレットの10色に固定 → シリーズとして揃う

### 8. 「見せる前提」を評価軸に入れた

このリポジトリのゲームは動画に映る。遊べれば成功ではなく、
**遊んでいない人が見て面白いか**を同じ重みで見る（[broadcast-design.md](../../design/broadcast-design.md)）。

仕組みとして落としたのは次の2つ。

- 面白さゲートに **`画面で何かが起きる間隔`** を追加した。
  上手いプレイ中にスコアが動く平均間隔を測り、無風が続くゲームを弾く（目安 0.25〜4秒に1回）
- 企画を出すときの様式に「権利面の注意点／映える瞬間／結果を見たくなるポイント／
  成否の見えやすさ」を含めた（`new-game` スキル）

### 9. 権利の線引きを規範と記録の両方に置いた

既存作を下敷きにする企画があるため、**遊びの仕組みを参考にすることと、
具体的な表現をコピーすることを明確に分けた**（[rights-and-originality.md](../../design/rights-and-originality.md)）。

- 規範: CLAUDE.md に「必ずオリジナルで作るもの」の一覧と、
  **寄りすぎに気づいたら黙って進めず指摘する**義務を書いた
- 記録: `meta.inspiration` に「何から着想し、何を借り、何を自作したか」を残し、
  ゲームページに表示する。`npm run fun` でも公開前チェックの案内が出る

「手元で作れること」と「公開してよいこと」は別で、後者を判断できるのは人間だけ、
という前提を仕組みの側に埋めてある。

### 10. サーバーを持たない

記録は localStorage。ログインもDBも API キーもない。
公開リポジトリに秘密情報を置かない前提とも噛み合う。

## 採らなかった案

| 案 | 理由 |
|---|---|
| 1ゲーム1リポジトリ | 共通ランタイムの更新が全体に届かない。一覧も作れない |
| React コンポーネントとしてゲームを書く | 純粋関数でなくなり、ボット試験ができなくなる |
| 物理エンジン・描画ライブラリの導入 | この規模の計算には要らない。依存が増えると制作が遅くなる |
| ドット風 Web フォント | 日本語フォントは数MB。拡大表示で十分ドットになる |
| ゲーム本体を一覧ページから静的 import | ゲームが増えるほどトップが重くなる。`loaders` で遅延読み込みにした |
