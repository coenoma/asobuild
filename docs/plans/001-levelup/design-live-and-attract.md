# 設計: 収録カンペ（/live）とアトラクトモード

> [proposal.md](./proposal.md) の #1 と #2。2026-08-11 着手。

## 何を解くのか

### #1 収録カンペ
開発実況の最大の敵は **dead air**（AIが作業している間、画面にコードが流れるだけで
何が起きているか視聴者に分からない時間）。
これを「いま何をやっているか」を常時映すカンペで埋める。

副産物として、**タイムスタンプ付きの編集台本**（何分に何が起きたか）が自動で残る。
テロップ原稿・チャプター作りがここから起こせるので、編集時間が減る。

### #2 アトラクトモード
タイトル画面の裏でボットがデモプレイし続ける。ゲームセンターの筐体と同じ。

- 開いた瞬間に遊び方が伝わる（説明ゼロの理解がさらに速くなる）
- 「AIが自分の作ったゲームを自分で遊んでいる」画そのものが番組的
- `bot()` を必須にしてある見返りが、視聴者に見える形になる

## #1 の設計

### データの流れ

```
npm run say -- "ゲート2回目、いく"   ┐
npm run phase -- じっそう            ├→ .live/status.jsonl（1行1JSON・追記のみ）
npm run fun -- hanko（自動追記）     ┘
                                          ↓ 500ms ごとに読む
                                    /api/live（dev専用）
                                          ↓
                                    /live（レトロ画面のカンペ）→ これを録画に映す
```

**追記のみのログにする理由**: 書き手（CLI・ゲート）と読み手（画面）が疎結合になり、
どちらが落ちても他方が壊れない。収録中に壊れないことを最優先する。

### イベント（1行1JSON）

```ts
{ t: 1723000000000, kind: 'say',   text: 'ボットが全滅した' }
{ t: ..., kind: 'phase', phase: 'じっそう' }
{ t: ..., kind: 'timer', action: 'start', seconds: 1500, label: 'ポテトM' }
{ t: ..., kind: 'gate',  slug: 'hanko', pass: false, checks: [{ label, pass }] }
```

イベント列から現在の状態を導出する（状態そのものは保存しない）。
途中から読み始めても最後まで再生すれば同じ状態になる。

### 画面

録画に映す前提なので 16:9。ガラケー液晶の配色（`keitai` パレット）を CSS で再現する。

```
┌────────────────────────────────────────────┐
│ アソビルド開発中     きかく▸じっそう▸けんてい▸しゆう │
├────────────────────────────────────────────┤
│                                            │
│      いまの一言（特大・これが主役）             │
│                                            │
├──────────────────┬─────────────────────────┤
│ のこり             │ めんどうさゲート           │
│ ▓▓▓▓▓▓░░░ 12:34  │ ✓ 再現性                 │
│                   │ ✗ 上振れがある            │
├──────────────────┴─────────────────────────┤
│ 12:01 ゲート2回目、いく                       │
│ 11:58 ボットが全滅した                        │
└────────────────────────────────────────────┘
```

### 本番に出さない

このリポジトリは PUBLIC で、本番サイトに開発用ページは不要。

- `/live` と `/api/live` は `NODE_ENV === 'production'` なら 404
- `.live/` は **gitignore**（作業ログが公開されるのを防ぐ）
- 台本として残したいときは `npm run live archive` で `docs/worklog/` へ手動で移す

### hooks で自動記録するか → 今回は入れない

Claude Code の PostToolUse フックでツール実行を自動追記する案もあるが、

- 粒度が粗く、騒がしくなりやすい（カンペは「読める密度」が命）
- 収録中に想定外の文字列が画面に出るリスクがある（PUBLIC・録画中）

まずは **手動 `say` ＋ ゲート自動** の2本で運用し、足りなければ後から足す。

## #2 の設計

`GameShell` のタイトルフェーズで、デモ用の state を別に持ち、`bot()` の入力で進める。

- 実プレイ用の state / rng とは完全に分ける（記録や進行に影響させない）
- デモが終わったら 0.8 秒おいて次のデモへ（毎回シードを変える）
- 描画は「ゲームを描く → 上から半透明の背景を重ねる → タイトル文字」の順
  （`Painter.alpha` のネストに頼らない。リザルト画面と同じ手法）
- 右上に小さく `DEMO`

**ゲーム側の変更はゼロ。** すでにある `bot()` と `advance()` を使うだけ。

### アトラクトモードの動作確認ができなかった理由

ブラウザ自動化から確認しようとしたが、`document.visibilityState === 'hidden'` /
`requestAnimationFrame` が毎秒0回だった。**Chrome は背面ウィンドウのタブでフレームを止める**ため、
この経路では動きのあるものを検証できない（同じ制約は前にも踏んでいる）。

実装が正しいと考える根拠は3つ。

1. デモを進める処理は `bot()` → `toInput()` → `advance()` で、
   面白さゲートの `playOnce` と同じ経路。**そのロジックは数百回の試行で検証済み**
2. 描画（`DEMO` 表示・裏の薄いゲーム画面）はスクリーンショットで確認できている
3. ループの構造は既存の playing フェーズと同一

**実機（手元のブラウザを前面にした状態）での目視確認は残っている。**

## 途中で見つけた別の問題（直した）

面白さゲートの「一気に遊びきれる長さ」が、試行80回で56分・200回で8分と**大きくぶれていた**。
最後の称号への到達回数が少ないと推定が粗くなるのが原因。

当て推量で合否を出すのをやめ、**到達5回未満なら「判定できない」と言って試行を増やすよう促す**
形に変えた。数字が足りないときに黙って結論を出さないほうが、ゲートとして信頼できる。

## やらないこと

- OBS 用の背景透過（まずはウィンドウごと映す運用で足りる）
- カンペの遠隔操作・複数端末同期（1台で完結させる）
