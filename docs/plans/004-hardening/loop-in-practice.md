# 学びが次に効くまでの一周（実例つき）

> このリポジトリの仕組みは「良いものを作る」ためではなく、
> **一度受けた指摘を二度受けない**ために組んである。
> ここは、その一周が実際に回った記録。次に同じことをするときの手順書として読む。

## 一周の形

```
  ① ゲートが緑になる          npm run fun -- <slug>
        ↓  ★ここで完成と言わない
  ② 人が遊ぶ                  npm run playtest -- <slug>
        ↓
  ③ fail と、その言葉が残る    docs/records/playtest/<slug>.json
        ↓
  ④ 原因を、実装まで特定する   「言われたこと」→「どのコードのどの判断か」
        ↓
  ⑤ 一般化してカタログに書く   docs/design/feel-catalog.md
        ↓
  ⑥ 次に必ず読まれる場所に置く .claude/rules/ ／ npm run status
        ↓
  ① へ（次のゲームは、この指摘を受けない状態から始まる）
```

**④ と ⑤ を飛ばすと、直っても学びが残らない。** そのゲームだけが良くなって終わる。

## 実例（`tamatsunagi` / 2026-08-12）

### ① ゲートは全12項目合格していた

上手いボット74秒・でたらめ17点・上振れ1.6倍。数字はむしろ良いほうだった
（同時期に作っていた `tamago` が4回調整して届かなかった水準）。

### ②③ 遊んだ人の言葉

> 輪っかを通したと思ったのにスルーされてるときがある？（成功だと思ったのに失敗、
> **バグなのか仕様なのかわからず**）とか、輪っかの色が変わることが**何を意味するのかわからなかった**

引っかかった問い: `終わったあと、指が勝手にもう一回押した？` → **いいえ**

### ④ 原因（ここがいちばん大事な工程）

言われたことをそのまま直すと、たいてい別のものを壊す。**なぜそう見えたか**まで降りる。

| 言われたこと | 実装で起きていたこと | 設計は間違っていたか |
|---|---|---|
| 通したのにスルーされる | 判定は「**針が届いた瞬間**の玉の位置」で見ていた。玉は横に揺れているので、撃ってから0.2秒で動く分を読む必要がある | **いいえ**（設計書に「動く分を読む」と明記された狙いどおりの挙動） |
| ↑ ではなぜバグに見えたか | **大きく外したときだけ何も表示されなかった。** 成功でも失敗でもない無反応 | **ここが間違い** |
| 色の意味が分からない | 色は高さ＝得点区分（黄5点／白3点／赤1点）。ラベルは描いていたが `color: 'line'`（最も薄い色）で事実上見えていなかった | **ここが間違い** |

> **設計を疑う前に、伝わり方を疑う。**
> ここで「読ませる設計が悪い」と結論して判定を甘くしていたら、
> このゲームの手応え（狭いところを通す緊張）そのものが消えていた。

### 直したもの

```ts
// 跨いだのに1つも通らなかった＝外した。
// ここで何も出さないと「通ったはずなのにスルーされた」と見える（遊んでの指摘）。
// どちら側に外したかまで出すと、次に何を直せばいいかが分かる
if (hit === 0 && crossed.length > 0 && n.mode === 'up' && s.judgeTimer <= 0) {
  const near = crossed[0];
  const off = tamaX(near) - LANE_X;
  setJudge(Math.abs(off) <= RING_HIT + 14 ? 'おしい！' : off > 0 ? 'まだ右' : 'まだ左', false);
}
```

点は動かさない。**反応だけ返す。** 色は凡例（色見本＋「5てん／3てん／1てん・きけん」）を画面に常設した。

### ⑤⑥ 残したもの

| どこ | 何を |
|---|---|
| [feel-catalog.md](../../design/feel-catalog.md) G章 | 「伝わらない」が起きる場所（無反応／凡例なし／薄い色／判定と見た目のズレ） |
| [fun-doctrine.md](../../design/fun-doctrine.md) ④ | 成功でも失敗でもない結果を作らない |
| [.claude/rules/games.md](../../../.claude/rules/games.md) | 出す前に見る落とし穴（チェックリスト） |
| `scripts/playtest-record.ts` | **指摘が上書きで消えないように履歴を持たせた**（下記） |
| `npm run status` | 「これまでに遊んで出た指摘」を一覧表示 |

## この一周で見つかった、仕組み側の穴

**指摘は、直して遊び直した瞬間に消えていた。**

`docs/records/playtest/<slug>.json` は最新の結果で上書きされる。
つまり fail → 修正 → pass と進むと、**学びの原料である fail のときの言葉が残らない**。
今回は人の記憶から手で写して残したが、次も同じ運を期待できない。

→ `PlaytestRecord.history` を追加し、実装の指紋が変わったときに前の記録を履歴へ送るようにした。
→ `npm run status` に「これまでに遊んで出た指摘」を出し、**新しく作る前に読む**導線にした
（[new-game スキル](../../../.claude/skills/new-game/SKILL.md) の冒頭でも読ませている）。

## 次に同じことをするときのチェック

- [ ] fail の言葉を、**直す前にそのまま引用して**残したか
- [ ] 「言われたこと」ではなく「なぜそう見えたか」まで降りたか
- [ ] 設計そのものを弱めていないか（伝わり方の問題を、難度で殴っていないか）
- [ ] 一般化して feel-catalog に書いたか（そのゲーム固有の話で終わっていないか）
- [ ] **次に必ず読まれる場所**（`.claude/rules/` か `npm run status`）に置いたか
- [ ] 直したら、**もう一度遊んでもらってから**公開したか（`npm run ship` が見ている）
